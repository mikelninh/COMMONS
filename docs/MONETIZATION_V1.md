# COMMONS Monetization v1

## Principle

**Commercial capability subsidizes a useful public commons.**

The public product should not become dependent on:

- ads
- outrage
- selling user data
- paywalling emergency information
- maximizing time-on-site

The thing organizations pay for is deeper operational capability.

## What stays public

- WORLD PULSE orientation
- public stories
- core evidence
- public Trust status
- public World Model research
- emergency understanding
- public-source limitations and corrections

## First paid job

Do not start with a giant self-serve subscription product.

Start with three design partners.

### Offer

A continuously maintained watchlist for up to ten public watchpoints.

Each watchpoint can include:

- physical state
- model comparison
- historical context
- declared alert thresholds
- source / freshness tracking
- evidence brief
- follow-up on what happened
- monthly backtest review

### Target customer

Teams where uncertainty is expensive:

- climate / resilience
- supply-chain operations
- logistics
- risk teams
- humanitarian operations
- research and analysis

## Pricing hypothesis

These are hypotheses, not current published prices.

### Design partner

**€500–1,500 / month**

High-touch service.

Goal: learn what organizations actually pay for before building billing infrastructure.

### Team product

Later target:

**around €299 / month**

Potential features:

- self-serve watchlists
- alerts
- collaboration
- history
- exports
- model disagreement
- backtest reports

### API / enterprise

Later:

**€2,000+ / month**

Potential features:

- API
- private datasets
- custom source connectors
- SSO / permissions
- audit controls
- higher limits
- procurement support
- reliability commitments

## Unit economics

Weather / hazard data is not expected to be the largest cost.

The largest costs will be:

- human review
- support
- reliability engineering
- source licensing
- private integrations
- sales / procurement

A sensible target is >80% gross margin on software/API revenue once the workflow is standardized.

## Current infrastructure budget

Research prototype:

**€0–50 / month**

Possible because most data sources are open and GitHub can host the public prototype.

Serious public beta:

**€100–500 / month**

Adds commercial data API where required, persistent database, monitoring, backups, scheduled workers, modest inference and alerts.

Dependable professional service:

**€500–2,000 / month**

Adds redundancy, stronger monitoring, larger historical evaluation jobs, managed database, alert infrastructure, paid data tiers and more robust compute.

Institutional service:

**€5,000–20,000+ / month**

Potentially includes multiple data vendors, regional redundancy, independent audits, SRE/on-call, enterprise security and higher SLAs.

People will dominate cost before weather APIs do.

## Commercial-data rule

Do not activate paid customer revenue while depending on a hosted provider's non-commercial endpoint.

Before the first paid design partner:

1. inventory every source licence
2. switch Open-Meteo to an appropriate commercial plan or direct-source ingestion
3. add required attribution
4. document procurement / vendor dependency
5. add provider-failure fallback

## Revenue milestone

The first meaningful target is not €1M ARR.

It is:

**3 organizations × one useful watchlist × recurring monthly payment**

If those teams renew because COMMONS repeatedly caught meaningful change and reduced analyst work, the paid job is real.

Then scale:

3 → 10 → 30 customers

before building a broad enterprise platform.
